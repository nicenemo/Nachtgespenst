## Core2 LED bar
- Hardware: M5GO Bottom2 (Core2 base): 10x SK6812 (GRB, 800 kHz, no white channel used) on **GPIO25** (M5 docs). GPIO15 is the *old* Core/Fire M5GO base, so our LED_PIN=25 is right for Bottom2; if nothing lights, the base may be the older one (GPIO15) -- `tools/ledtest` drives both.
- Power: LEDs run from M-Bus 5V, which on Core2 is the AXP192 EXTEN/boost. M5Unified enables it by default (`cfg.output_power=true` -> `M5.Power.setExtOutput(true)`; AXP192 reg 0x90 GPIO0 LDO + EXTEN), except it refuses when on battery-only with level <=8%. Call `M5.Power.setExtOutput(true)` explicitly after `M5.begin()`. Check ui.cpp calls M5.begin with default config (output_power true) BEFORE FastLED.addLeds. Data line is 3.3V into a 5V SK6812: usually OK on the base (level-shifted/short).
- FastLED 3.10.3 on ESP32 uses RMT; M5Unified (Core2) and LVGL do not use RMT, no conflict known. GPIO25 is not used by display/audio/touch on Core2. FastLED.show() blocks ~0.3 ms for 10 LEDs (interrupts briefly); fine.
- Current: ~60 mA/LED at full white = 600 mA; keep `setBrightness(<=40)` (~25%) on battery/USB.
- Test project: `tools/ledtest/` (build `PLATFORMIO_CORE_DIR=$PWD/.pio/core .pio/venv/bin/pio run -d tools/ledtest`); loops GPIO25 then GPIO15: each LED R/G/B, then mixes; prints `PIN n` on serial and LCD.
- Locks-page design: per-lock colour table `LOCK_COLORS = {Caps orange(255,80,0), Num green(0,220,60), Scroll blue(40,80,255)}` (same as ui.cpp). Bar split in 3 segments (LEDs 0-2 / 3-6 / 7-9, or 10 LEDs as 4/3/3); active lock fills its segment with its colour; when >1 active, additive mix: each LED = sum over active locks `qadd8` of the colour of locks covering it, with blend zones, or simply mix all active colours across the whole bar. Tile background = lock colour (dim when off). API proposal in LedColors.h:
  `CRGB lockColor(LockId)`; `void ledBarLocks(uint8_t activeMask /*bit0 caps,1 num,2 scroll*/)` (renders segments + additive mix into g_leds); `CRGB mixColors(const CRGB* c, uint8_t n)` using `qadd8`.
